# Agent 需要的不只是聊天记忆

过去一年大家谈 AI 记忆体，很多时候其实是在谈“把聊天记录记得更久”。用户喜欢什么、正在做什么、上次聊到哪一步，系统记下来，下次接着说。

这当然有用。

但 Agent 需要的不只是这个。

我最近在做一个 TraceDB，叫 [yiTrace](https://github.com/vibeinging/yiTrace)。一开始想得很直接：Agent 跑起来以后，总得知道它做了什么。它调用了哪些工具，哪一步失败了，哪次重试浪费了 token，哪个流程最近开始不稳定。如果没有这些记录，排查问题基本靠猜。

做着做着，我越来越觉得：TraceDB 不只是可观测性工具，它也是 Agent Memory 很重要的底座。

因为 Agent 真正值得记住的东西，很多不在聊天记录里，而在执行过程里。

## Chat Memory 记的是人

Chat Memory 更像是在回答：“这个用户是谁？”

比如：

- 用户喜欢中文回答。
- 用户在做某个项目。
- 用户不喜欢太 AI 味的文案。
- 上次对话停在某个方案。

这些记忆解决的是关系连续性。没有它，助手每次都像第一次见你。

但它还不是 Agent 的“经验”。

Agent 不是只在聊天框里说话。它会查文档、读代码、改文件、跑测试、调用工具、失败、重试。有时候最后只回你一句“已完成”，但真正有价值的东西，其实藏在它中间做过的那些步骤里。

## Agent Memory 记的是做事经验

举个例子。

用户让 Agent 接入一个本地数据库包。最后对话里只留下：

> 已接入，测试通过。

如果只看聊天记录，memory 最多记住“用户要接入数据库包”。但如果看执行过程，可能会发现更有价值的经验：

```text
任务：接入 @yitrace/db

读 package.json
运行 npm test，失败：找不到 darwin-arm64 native binding
检查 Node 运行环境：darwin arm64
检查产物：实际生成的是 x86_64 的 .node 文件
修改本地构建脚本：根据 Node arch 显式选择目标平台
重新测试：通过
打 tarball，用干净项目验证 ESM / CJS / native 加载：通过
```

这时真正该记住的不是“数据库包接好了”，而是：

> macOS arm64 上调 Node native 包时，如果报找不到 binding，不要只看 npm 依赖。要同时检查 Node 运行平台和实际生成的 `.node` 文件架构。修好以后，最好用一个干净项目重新安装 tarball，验证 ESM、CJS 和 native 加载都能跑。

这就是 Agent Memory。

它不是用户偏好，而是工程经验。它有触发条件，有适用范围，也有证据。下一次遇到类似问题时，Agent 如果能先想起这条经验，就能少绕很多路。

## 为什么需要 TraceDB

很多 memory 系统的问题不是记不住，而是太容易记错。

模型很容易把一次偶然失败总结成规律，把过期接口当成长期事实，把临时做法写成永久建议。短期看像“更聪明了”，长期看可能会污染 Agent 的判断。

TraceDB 的作用，是给 memory 一个事实底座。

它记录 Agent 当时到底做了什么：用了哪些工具，输入输出是什么，哪里失败了，后来怎么修好，最终结果是否成功。memory 可以从这些记录里提炼经验，也可以被新的记录反证。

这里还有一个很现实的数据库问题：Agent trace 很容易膨胀。

一次任务可能有几十上百个工具调用，每次调用又有输入、输出、错误、耗时、token、成本。如果只是把它们当成一坨 JSON 日志存起来，很快就会变得又大又难查。你想按项目、工具、状态、时间、成本筛一下，都可能要扫很多无关内容。

yiTrace 要解决的正是这类问题。它不是简单把 trace 写进文件，而是按更适合查询的方式组织数据：常用来过滤和聚合的字段可以像列一样被单独读取，大块输入输出可以晚一点、按需再取。这样既能保留完整执行现场，又能缓解数据膨胀，不至于 trace 一多就查不动、存不起。

所以我现在更倾向于这样理解：

> Agent Memory 不一定一开始就必须有 TraceDB，但如果它想变成可靠的长期经验系统，而不是聊天摘要的另一个名字，就需要 TraceDB 或类似的执行记录。

没有执行记录，memory 只能说“我觉得这是经验”。有了执行记录，memory 才能说“这条经验来自哪些真实任务，后来有没有被推翻”。

## 记忆不能只会增加

Agent Memory 还有一个很现实的问题：它不能只往里塞。

以前好用的经验，后来可能失效。以前某个工具经常失败，后来可能修好了。以前某个测试流程必须全量跑，后来项目拆分以后可能只需要跑相关测试。

所以好的 Agent Memory 应该会更新、降权、过期，甚至删除。

比如这两条记忆看起来冲突：

- 发布前必须跑完整测试。
- 小改动只跑相关测试即可。

它们不一定谁对谁错，可能只是适用场景不同。第一条适合发版，第二条适合本地开发。系统要做的不是简单覆盖，而是把范围分清楚：什么时候用哪条，最近有没有反例。

这也是 TraceDB 的价值。它能不断提供新的执行结果，让 memory 被验证，而不是写进去以后就永远正确。

## 还要注意隐私和成本

Agent 的执行记录里可能有敏感信息：API key、数据库结构、内部错误、客户数据、私有代码。不是所有 trace 都应该进入长期记忆。

真正能用的 Agent Memory，一定要有边界：哪个项目的记忆只能在哪个项目用，哪些字段要脱敏，哪些内容只能留在 trace 里，不能被总结进 memory。

成本也要控制。不是每条 trace 都值得让模型总结一遍。更合理的方式是先用规则筛掉普通成功路径，只挑失败、重试、成本异常、结果变化明显的任务做提炼。短任务可以及时处理，长任务可以延后处理。

简单说，Agent Memory 应该是一个精炼系统，不是一个什么都收的垃圾桶。

## yiTrace 和 MemMe 怎么分工

如果落到我现在做的两个项目，[yiTrace](https://github.com/vibeinging/yiTrace) 和 [MemMe](https://github.com/vibeinging/MemMe)，我会这样分工：

```text
yiTrace：记录发生了什么
MemMe：总结从中学到了什么
```

yiTrace 做 TraceDB，负责把 Agent 的执行过程记清楚、查得到、能回放。它应该保持克制，先把记录、查询、检索、成本、结果、列式存储和数据膨胀控制这些基础能力做好。

MemMe 则可以往 Agent Memory 走，从 yiTrace 这样的执行记录里提炼经验，再在下一次任务前召回。它不应该只记“用户说过什么”，而应该能记“这个 Agent 上次怎么做成了，怎么失败了，下次应该避开什么坑”。

这两个项目最好不要互相吞掉。TraceDB 太早塞进复杂 memory 逻辑，会变重；memory 直接读数据库内部文件，又会把自己绑死。更好的方式是通过公开 API 连接：yiTrace 提供证据，MemMe 提炼经验。

## 最后

Chat Memory 让 AI 记得你是谁。

TraceDB 让我们看清 Agent 做过什么。

Agent Memory 则应该让 Agent 记得自己是怎么做事的。

这三件事有关联，但不是同一件事。

如果 Agent 未来真的要长期工作、持续改进、少犯重复错误，它需要的不只是更长的聊天记录。它需要能回到执行现场，从成功和失败里提炼经验。

这也是我觉得 TraceDB 和 Agent Memory 很搭的原因。
